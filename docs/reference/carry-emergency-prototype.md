# Loaded carrying emergency prototype

This development experiment is disabled by default. `--wildfire-enable-carry-emergency` enables new admissions for the reviewed installed native build. An already-saved active executor still restores its ownership when the switch is absent. Natural ignition and the existing unsupported civilian exposure path are unchanged. This is not release-complete civilian fire safety.

## Implemented boundary

One exact job is supported: a living outdoor adult already walking a native CarryRootBehavior delivery, using its own WalkToAccessibleExecutor, with existing carried goods and a matching native destination capacity reservation, no source stock reservation, no critical need and no player control. Production/consumption cargo, pickup trips, stationary work, needs jobs, children and arbitrary mod executors are not admitted. The original GoodCarrier and GoodReserver retain all goods, cargo accounting type and reservations. There is no second ledger, reservation reconstruction, consumption or cargo deletion.

The compatibility adapter checks approved native binary hashes, exact method/field signatures and unique same-entity executor names. Native IExecutor names use Type.Name, so the persistent class is named WildfireCarryEmergencyExecutor. A standard TickableComponent runs before the native late BehaviorManager. Admission reads the actual remaining PathFollower path using reviewed `_pathCorners` and `_nextCornerIndex`, prepending the current transform; recomputing a safe alternative is not evidence that the current installed route is safe.

A native NavMeshObserver can refresh a path after our ordinary interceptor. StartedNewPath may also claim an **existing exact** native delivery, but never a new native Carry.Decide launch: ProcessBehaviors has no running executor while deciding that launch. The reviewed WalkToAccessibleExecutor.Tick does not call FindPath or raise this event. Callback admission rechecks the full native owner/cargo/lifetime predicate before swapping to the registered emergency executor, then disables the late mover without clearing the path. FindPath continues only its path/destination bookkeeping. The next ordinary tick stops/replans coherently. This callback does not admit arbitrary executors or recursively admit our own escape/delivery launch.

Owned movement uses [the shared native stop boundary](native-owned-walker-stop.md). New or refreshed escape/delivery paths are checked from the real transform against installed path corners. Rejection pauses the late mover while retaining the path until FindPath returns. Actual position and safe refuge are checked separately from native Stopped. The prototype reuses FireSafetyField's cached observations and safety policy; it adds no third GPU readback and does not claim civilian balance is established by the warden thresholds.

At a safe refuge, delivery can resume only after the same native capacity reservation still matches and a fresh native WalkToAccessibleExecutor.Launch installs an accepted route, or reports Success with physical arrival at a real target access. Only then is manager ownership returned to native carrying. Native Carry.Decide is never invoked directly, and the old walk is never ticked against an escape destination. A rejected path is not accepted merely because native Launch reports Success.

## Lifecycle and limits

The registered executor owns only Escaping/Holding state, reason and elapsed hours. BehaviorManager saves its existing CarryRootBehavior reference plus this executor name and invokes its Save/Load. Native GoodCarrier/GoodReserver save their own state. Load deserializes and marks replan without touching animation/movement; after native entity loading settles, the first ordinary owned tick verifies exact manager behavior and executor identity, stops and plans from the current world. Native saved path coordinates are not replayed as authority. Unknown schema/build/name or incompatible active state rejects, rather than silently handing a half-owned job back.

The process switch affects new admissions only. Current jobs continue recovery using available observations even when ordinary Wildfire dispatch is disabled. Death releases to native root priority, leaving death goods/reservation semantics native. Explicit player control wins over this development emergency; it gets a coherently stopped walker, with native goods untouched. Save guards reject in-flight or indeterminate transitions even if the affected entity was deleted. Unexpected post-launch failure always pauses late movement irrespective of logical phase; it clears native destination/path only while exact emergency behavior/executor ownership remains. If ownership already changed, retaining the foreign path avoids turning cancellation into apparent native arrival. A nested path exception unwinding through the enclosing transition gets one cleanup attempt, including when cleanup fails. The guard records the original cause and any stop failure, blocks saves and prevents automatic retry. Because the poison guard is session-wide, every other active emergency also pauses its late mover at the next ordinary interceptor tick; it retains native ownership and reservations without retrying the failed transition.

The selected beaver panel reports escape, trapped/unavailable or stranded delivery status and explicitly warns: prolonged Holding can block eating/drinking. Missing/deleted destination, reservation invalidated during load, or no safe delivery route keeps cargo in native hands. This is a **release blocker**, not the final recovery policy. Next investigate depositing a native loose-good stack at a safe refuge, then releasing destination capacity and native needs. Do not silently destroy cargo or let native CarryRoot fallback EmptyHands stand in for recovery. That next resource mutation needs its own verified native transaction/persistence plan.

## Evidence and validation

Actual Claude Sonnet 5 reviewed the design and supported the narrow version-checked component seam without Harmony. Accepted review points include name uniqueness and critical-needs starvation. Its stale-Stopped concern was resolved directly in native IL: GoTo resets the stop flag and synchronously installs destination; elapsed time or nonzero path length would not prove arrival. A later Claude stop review independently flagged Idle Load; coordinator fixes made Idle no-op and deferred active physical restoration until an owned tick. The corrected carrying snapshot then received an actual tools-disabled Claude Sonnet 5 review (one successful turn, no permission denials). Its concrete duplicate-cleanup and foreign-owner-stop findings produced the guarded-unwind and ownership-aware freeze fixes above. Signature-symmetry and unused status suggestions did not establish correctness defects; exact binary fingerprints already cover native WalkToPosition, and the installed IExecutor contract explicitly declares Save/Load. No missing-persistence-interface defect exists.

Focused tests cover invalid/successful route receipts, lost reservation/refuge rejection, corrupt save state, in-flight save, partial transition failure after a logical release, failed cleanup preserving the original cause, and rejection of an unknown native binary. The native field test uses isolated uninitialized managed fixtures to prove actual approved field swaps, foreign owner/behavior rejection, no callback admission at a new behavior decision, duplicate executor name rejection and correct remaining-path suffix. An additional installed-native fixture proves failure after handing ownership back pauses the mover while preserving foreign destination/path and native Stopped=false; an owned failure still invokes coherent native stop. The nested-callback regression proves one cleanup attempt even when animation cleanup throws, without preventing another actor from pausing after the shared fault. It does not construct a game entity or execute navigation.

No gameplay or save/reload proof has occurred for this prototype. The sole Live QA Controller must validate copied saves: native loaded carry A→B; route ignition; ownership and actual escape; exact goods/capacity held; saves while Escaping and Holding; fresh native delivery exactly once after clearing fire; deleted destination, no escape, missing restored reservation, death, player control, flag removed, unknown fingerprint and critical-needs diagnostics. Movement interpolation, stacked access routes and scheduler/event integration remain live proof requirements.
