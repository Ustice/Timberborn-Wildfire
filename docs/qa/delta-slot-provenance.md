# Originating local slot in GPU deltas

`CellDelta(CellIndex, OldCell, NewCell, TargetId=0, SlotId=0)` carries the owner and stable local material slot that existed when the GPU emitted the event. The append row is five explicit uint32 words: index, old packed cell, new packed cell, target, slot (20 bytes). Both compute backends and the standalone Unity capture runner use this shape. Ordinary command rows remain 16 bytes; material requests/receipts remain 40 bytes. Delta element capacity is unchanged; buffer memory increases by four bytes per allocated delta.

`AppendDelta` captures both identity buffers at emission. Ordered ordinary commands append before the final material handoff marker; the handoff itself has its dedicated receipt and emits no administrative delta. Later simulation appends under the replacement identity. Two events at the same world cell and TargetId can therefore belong to different SlotIds and need not chain their packed values across the handoff.

Within the single ordered external-input kernel, repeated commands for the same originating slot preserve their execution order. Simulation appends across different cells remain unordered; snapshot comparison still treats those rows as an unordered collection and now includes SlotId. Native consumer normalization and per-body accounting are separately owned and must use the full origin rather than infer a slot from the present cell.

Old C# constructors and JSON captures that omit SlotId default to zero, meaning unknown legacy provenance. No slot is inferred from final fields or the current registry. The new raw GPU reader always requires five-word rows; it does not guess between old and new strides. New owned GPU events read the actual nonzero material slot from the initialized buffers.

Managed checks cover 20-byte stride/native Marshal offsets, multi-row readback, truncated-row rejection, full identity JSON round trips/comparison and explicit old JSON defaults. The licensed fixture and actual native factory probe perform fuel8→6→2 as two ordinary events for slot701 (fixture slot11), followed by a same-target handoff and simulation3→0 for slot702 (fixture slot13). The first two events chain within their originating slot; the third starts from a different material definition. Actual engine results and exact revision must accompany this protocol change. No live world deployment is implied.
